# Decisions

Decisions made while building without anyone to ask. Newest at the bottom.

1. **Project location / git.** The session already runs inside the git repository `Zignifikant-help`, on branch `claude/bilagsmatch-setup-8yawi8`. Instead of `git init` (which would create a nested repository) the app lives in the `bilagsmatch/` subfolder and is committed to that existing repository and branch.
2. **Versions.** Pinned exact versions. Chose mature, well-known majors over brand-new ones where the newest major is days old or a release candidate:
   - Next.js 16.4.6 (latest stable), React 19.2.3.
   - TypeScript 5.9.3 (TS 7 is the new native compiler; Next's type-check integration targets 5.x).
   - Prisma 6.19.3 (Prisma 8 is an RC; 7 requires driver adapters and a different generator). Enums and Json work on SQLite in 6.x and are Postgres compatible.
   - next-auth 4.24.15 (the `latest` tag; v5 / Auth.js is still beta). Credentials provider, JWT session in an HTTP-only cookie.
   - Vitest 3.2.4, ESLint 9.39.1 (flat config), Zod 4.6.7 (upgraded from 4.1.12 because of a security advisory), Tailwind 4.1.16.
   - @playwright/test 1.63.0 to match the Chromium build pre-installed in this environment.
   - @anthropic-ai/sdk 1.5.0 (newest 1.x that has been out for ~2 weeks).
3. **shadcn/ui.** The shadcn registry (ui.shadcn.com) is blocked from this environment, so the shadcn components that are used (Button, Input, Label, Card, Badge, Dialog, Table, Textarea, Select) are written by hand in `src/components/ui/` following the shadcn source style (cva + tailwind-merge + Radix Dialog). Native `<select>` is used for dropdowns because it is fully accessible and keyboard friendly without extra dependencies.
4. **Tenant isolation.** Every tenant-owned table has an `organizationId` column (denormalised from Client where needed). `forOrg(organizationId)` returns a Prisma client extension that injects `organizationId` into the `where` of every read/update/delete and verifies it on every create. Route handlers only get data through this client. This makes forgetting a scope check a type/runtime error instead of a data leak.
5. **Money range.** Amounts are Prisma `Int` (32-bit) øre, i.e. max ±21.474.836,47 kr per amount. Larger amounts are rejected by validation with a clear message. Enough for receipts/bank lines of a small webshop; would move to BigInt for larger clients.
6. **Dates.** Date-only values (invoice date, booking date) are stored as `DateTime` at 00:00 UTC and always formatted in UTC, so there is no time-zone drift.
7. **`prisma migrate reset` and AI agents.** Prisma 6.x refuses to run `migrate reset` when it detects it is being run by an AI agent, unless the user gives explicit consent. I did not bypass that guard. `npm run db:reset` is still the conventional `prisma migrate reset --force` + seed, meant to be run by a human. The test suites never call it: they delete their own throwaway database file (`prisma/test.db`, `prisma/e2e.db`) and run `prisma migrate deploy`. I verified the reset flow with the equivalent non-destructive steps on a fresh database (`prisma migrate deploy` + `npm run db:seed`).
8. **Route handlers + services instead of server actions.** All mutations go through JSON route handlers under `src/app/api`, wrapped by `authed()` (auth check + error mapping). Business logic lives in `src/lib/services/*` and is shared by pages and routes. Integration tests call the real route handlers with a mocked session, which tests auth and org isolation end to end.
9. **Matching assignment: greedy best-score-first.** The candidate graph is sparse (the amount filter leaves very few candidates per document) and scores are well separated, so greedy gives the same result as an optimal assignment on realistic data and is easier to explain. Ties are broken by amount points, then day distance, then id, so results are deterministic. The Hungarian algorithm is a possible later improvement.
10. **Scoring weights.** Amount 55 (exact) / 50 (±1 kr.) / 40 (foreign currency within 5 %) / 55 (original foreign amount appears in the bank text). Date up to 25. Supplier-name similarity up to 15. Invoice number in the bank text +15. Score capped at 100. An exact amount on the same day with an unknown text gets 80 ("Tjek venligst"). A recognisable supplier lifts it above 85.
11. **Foreign currency rates.** Fixed approximate reference rates (`APPROX_DKK_RATES`, DKK per 100 units) instead of a live rates API, because the app must work offline. DKK is pegged to EUR, so EUR is accurate. For other currencies the ±5 % tolerance absorbs the approximation and card fees.
12. **Date window.** A pair is allowed if the transaction falls within −3…+45 days of the invoice date _or_ of the due date. Points use whichever anchor is closer. This also accepts invoices with long payment terms that are paid late.
13. **Journal entries.** One line per confirmed match. `amountOre = −bankAmount`, so an expense is a positive debit on the chosen account and the client's bank ledger account (default 5810) is the counter account. Voucher numbers run per client.
14. **Rule learning.** On confirmation the most specific available key is learned: CVR, otherwise the normalised supplier name, otherwise a bank-text word. If the same rule gets a different account or VAT code, the latest decision wins and the counter resets to 1.
15. **Duplicate uploads** of identical content (same SHA-256 for the same client) are idempotent: 200 with `duplicate: true`, nothing stored. A 409 would show up as a console error in the browser.
16. **Extraction structured output.** The Anthropic provider uses `output_config.format` with a JSON schema, then validates with Zod (and retries once with the Zod errors). The SDK's own retries are disabled (`maxRetries: 0`) so backoff is explicit and testable. Server-side model fallbacks were not enabled because the model is configurable through `ANTHROPIC_MODEL`. A refusal is handled by marking the document FAILED with a Danish message.
17. **Job queue.** A DB table plus an in-process worker started from `instrumentation.ts`, 3 jobs at a time, polling every 1.5 s, with an immediate kick when a job is enqueued. Retryable errors back off 30 s → 60 s, with up to 3 attempts. Chosen over `p-queue` because job state survives restarts.
18. **E2E runs against a production build** (`next build && next start` on port 3100, fresh `prisma/e2e.db`). This makes it stable and close to production. Hydration warnings only show in development, so `npm run smoke:dev` runs a separate dev-mode check (it found and fixed one issue).
19. **Seed data is generated** (PDFs with pdf-lib, bank CSVs in Danske Bank and Nordea style) from one catalogue (`src/lib/seed/sample-documents.ts`). The mock extraction provider uses the same catalogue, so the PDFs, the mock data and the bank lines always agree. The seed imports the CSVs through the same preview/import service the UI uses.
